### DSH 卡死与代理路径

启动故障包含 resolve hook 重入、宿主 schema API 兼容和目录读取无法及时结束等问题。目录错误不能让整个模型选择器一直等待；超时后保留 fallback 或已知目录，并明确记录来源，不能把 fallback 当成 VM 目录读取成功。

DSH `0.2.1-rc.5` 的 `dsh-experimental-inspector` 会用 `new Request(input, init)` 包装全局 `fetch`，再只把 `Request` 交给原 `fetch`。Node 的扩展参数 `dispatcher` 因此丢失，可能出现启动目录预热走代理、随后推理改为直连的情况。插件现在使用自身 `undici.fetch` 与 `ProxyAgent`，不依赖宿主全局 `fetch` 包装器保留该参数。

该判断已有不联网的真实观察器函数 replay。原 Inspector 选定文件的 REA Evidence 为 `ev_000df5d6eb1b671da931d59f15bcd502611a43a7a982085fa66373951f635f87`，覆盖范围仅为选定文件。绕过观察器的 gateway 请求以插件目录日志和 VM 请求日志核对，不能再依赖该观察器显示完整网络情况。

用户指的是 Codex **桌面 App 发往模型服务的请求体压缩**，不等于独立 CLI 的行为，也不等于服务端响应压缩。

## Cloudflare / WARP 决策

本轮保持现有 HTTPS 入口，不接入 CF、不安装 WARP。先让源站具备大请求、解压、内存准入、并发、超时和可观测能力，再用实际负载判断是否需要更换入口。

CF 的边缘网络和平台限制不能替代源站保护。即使边缘接收上传，VM 仍需读取、解压和解析请求；压缩后的较小传输体也可能对应很大的解压体。多个请求同时进入时，源站仍可能因 body 缓冲、字符串或 JSON 对象副本超出内存。源站必须自行限制这些资源。

入口链路与 VM 到上游的出口链路分别测量。WARP 的出口路由变化不会自动解决本机到入口的上传瓶颈，也不能用一次较快请求证明持续收益。VM 上游代理的连接状态和节点健康同样不能从网关总处理时间直接推断。

若后续测试 CF，应保留现入口并增加测试入口，使用上述 20MB、30MB、50MB 负载比较上传耗时、首 token、P95 和完整流成功率，覆盖晚高峰。WARP 的出口测试另行进行，避免同时修改入口和出口后无法判断收益。当前尚未执行这些 CF / WARP 对照测试。
